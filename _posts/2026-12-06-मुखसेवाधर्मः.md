<div class="prose-text" markdown="1">

### What this post is about
**Backend-for-Frontend (BFF)** is a client-specific API layer that aggregates and shapes backend calls for one UI family without turning into a second monolith.

### Topics covered
1. One generic API chat tax  
2. Granularity by client family  
3. UI-shaped payloads  
4. Fan-in with bulkheads and deadlines  
5. Session handling at BFF  
6. Keep business invariants downstream  
7. Co-version with slow clients  
8. Auth-keyed caches  
9. Fan-in tracing  
10. Gateway vs BFF vs strangler  

### Sanskrit title
**मुखसेवाधर्मः** = *mukha-sevā-dharmaḥ* "dharma of the face-service" (BFF).

### English
Minimizable; Sanskrit-first.

### ग्राह्यम् / Keep
१. **one BFF per client family**: not per screen  
२. **shape DTOs for the UI**: no raw domain dump  
३. **parallel fan-in under deadline**: bulkhead deps  
४. **keep deep invariants in domain services**: thin BFF  
५. **compat for slow mobile trains**: version gates  
६. **cache only with auth/tenant keys**: no mix  
७. **trace each downstream hop**: not only BFF p99  

### त्याज्यम् / Avoid
- one public API forcing 20 mobile round-trips  
- BFF owning all money invariants forever  
- anonymous shared cache of personalized graphs
