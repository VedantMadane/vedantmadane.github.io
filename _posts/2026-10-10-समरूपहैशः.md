<details>
<summary>English · overview and topics (minimizable)</summary>
<div class="prose-text" markdown="1">

### What this post is about
**Consistent hashing** assigns keys to nodes so cluster membership changes move only a small fraction of keys.

### Topics covered
1. Pain of hash%N on resize  
2. Hash ring model  
3. Virtual nodes  
4. Minimal rebalance  
5. Replica successors  
6. Stable business keys  
7. Hot-key limits  
8. Shared algorithm/membership  
9. Cache invalidation on move  
10. Tenant hashing / cells  

### Sanskrit title
**समरूपहैशः** = *samarūpa-haiśaḥ* "consistent/uniform hash".

### English
Minimizable; Sanskrit-first.

<div class="prose-text" markdown="1">

### ग्राह्यम् / Keep
१. **shared ring view**: same algo+membership  
२. **vnodes**: smooth load  
३. **stable key**: business id not random each call  
४. **R successors**: document replica placement  
५. **hot-key plan**: salt/split/cache  
६. **transition reads**: dual-read or invalidate  
७. **ops runbook**: node join/leave steps  

### त्याज्यम् / Avoid
- hash%N as only shard plan on elastic clusters  
- different clients with different vnode counts  
- ignore hot keys
