<details>
<summary>English · overview and topics (minimizable)</summary>
<div class="prose-text" markdown="1">

### What this post is about
**Shadow traffic** (dark launch) forks a live request onto a candidate implementation while the client still receives only the primary response. It is evidence collection not a release. It sits before canary because no user is served by the new path.

### Topics
1. Why copy live traffic instead of synthetic replay  
2. Never return the shadow reply to the client  
3. Diff status latency and a stable body digest  
4. Sample inside a capacity budget  
5. Ban billing mail and other mutating effects  
6. Same authorization and redaction as primary  
7. Coordinate idempotency if any write can fire  
8. Instant flag kill when diffs explode  
9. Stay dark until parity then a tiny real slice  
10. Shadow versus canary versus blue-green  
11. Five operating limbs  
12. Close  

English is minimizable. Verse lines are pure Devanagari padya.

<div class="prose-text" markdown="1">

### ग्राह्यम् / Keep
१. **primary-only client response**: shadow never answers the user  
२. **active parity diffs**: status latency digest not blind fire  
३. **sample inside a budget**: protect origin and shared stores  
४. **no billing or mail side effects**: unless a full dry-run sandbox  
५. **same authz and redaction**: a looser copy path is a leak  
६. **instant flag off**: waiting for a deploy is too slow  
७. **shadow before canary**: evidence first then a real slice  

### त्याज्यम् / Avoid
- return shadow responses to users  
- full-rate shadow with no capacity plan  
- shadow a payment or mail path without a sandbox
